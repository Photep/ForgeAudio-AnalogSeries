<objective>
Build the D-07 compile canary that makes ROADMAP success criterion 3 real: proving that `make strict` and the CI MinGW **link** leg actually cover VCO code.

Why a dedicated translation unit is required: both gates only compile headers reached through a `.cpp`. Nothing in `src/` includes `VcoCore.hpp` in Phase 29 (`AnalogVCO.cpp` is Phase 30), so without a canary both gates would report PASS while covering no VCO code at all.

Why the canary must do more than `#include`: a translation unit that only includes a header **emits no code**. Header-defined inline and member functions are instantiated only when used, so nothing is ODR-used and the link leg has nothing to resolve. Such a canary is permanently, silently green and satisfies neither D-07 nor criterion 3 (P-1). The canary therefore ODR-uses the headers from an external-linkage function with a runtime-dependent argument, which defeats constant folding and dead-symbol elimination.

Why placement is an operator decision: this is the only Phase 29 change that can reach the released plugin binary. Task 1 surfaces the trade-off with a recommendation before anything is written.

What this plan can and cannot prove locally, stated honestly: `make strict` is a real, locally-runnable, hard-failing C++17-ism gate — verified during research against `inline constexpr`, `if constexpr`, `[[maybe_unused]]` and `std::clamp`. The **ODR/link class has no local substitute**: Apple clang links the exact v2.0.0 failure class cleanly at both `-O0` and `-O3`, materialising the in-class array as a per-translation-unit local symbol. No task in this plan asks for a local ODR reproduction, because such a task would silently pass. That negative control is a CI-observed checkpoint in plan 29-05.

Purpose: satisfy requirement TEST-06 and ROADMAP success criterion 3.
Output: the canary translation unit, `tests/check_canary.sh`, and a new `toolchain-gate` CI step that invokes it.
</objective>
