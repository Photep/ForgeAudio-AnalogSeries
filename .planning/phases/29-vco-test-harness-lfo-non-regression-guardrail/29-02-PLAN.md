<objective>
Harden the shipped-LFO golden replay into a tripwire that cannot be defeated silently — the D-04 half of TEST-04.

The existing six golden replays in `tests/test_golden.cpp` catch *behavioral* drift only if a change alters replayed output. They do not catch the "just regenerate the goldens" path. D-04 closes it: record the SHA-256 of every `tests/golden/freerun_*.f32` and hard-fail if the bytes ever change.

Mechanism (RESEARCH § "Tripwire Design (D-04)" Option A): a vendored, test-scope SHA-256 in `tests/Sha256.hpp` plus doctest cases in a **new** `tests/test_lfo_guardrail.cpp` whose expected digests are hard-coded string literals. Rationale for each half of that choice:
- **In-test, not a shell step** — ROADMAP criterion 1 requires a single `make test` run to prove the LFO canary; a shell hash step would not run there, and `sha256sum` does not exist on macOS.
- **Digests as source literals, not a data file** — changing a golden then requires a *code* diff, which is the entire point of D-04.
- **A new TU, not an edit to `test_golden.cpp`** — R-3: `test_golden.cpp` is its own only witness, so hardening it by editing it would let the same edit weaken the comparison. It stays byte-unchanged and is itself hash-pinned by plan 29-04.

A guard that has only ever been observed green is unvalidated. This plan therefore ships the negative control as **permanent automated cases**: published FIPS 180-4 vectors, and a one-byte-perturbed in-memory copy of a real golden that must hash differently.

Purpose: satisfy ROADMAP success criterion 1 and requirement TEST-04.
Output: `tests/Sha256.hpp`, `tests/test_lfo_guardrail.cpp`, `tests/golden/SHA256SUMS`.
</objective>
