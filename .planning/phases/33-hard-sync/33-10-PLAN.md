State the mechanism actually used and state its precondition: the reconstruction is exact only while the sync correction deposits nothing forward, which is a property of the placement plan 33-06 landed, and if a later phase changes that placement this renderer must reconstruct from both halves instead. Also state what this tool is NOT: not a golden, not a fixture, not committed — a rendered pair captured from one toolchain must never become a reference, and generating on demand into an ignored directory is what enforces that by construction rather than by discipline.

Structure, in four parts:
  1. A RENDER-POINT TABLE — a small struct plus an array, shaped like the spectral grid's cell struct: sample rate, master frequency, master edge shape, master/slave ratio, slave pitch, morph, character, a human-readable label used in the output filename, and a duration. Populate it from the sub-grid points plan 33-05 measured, so what the operator hears is what the gate measured. Keep the table separate from the rendering code — that separation IS the reusability the next phase needs
  2. A CORE-CONFIGURATION PAIR — the renderer takes two configurations and renders both. For this phase the pair is the shipped core and the same core with the sync correction withheld; the next phase's audition-gated value will supply a different pair without touching the renderer. Express the pair as data, not as a branch inside the render loop
  3. THE RENDER LOOP — drive the real core, one pass per render point, supplying the master voltage through the per-sample input functor. Accumulate the shipped sample and the reconstructed withheld sample simultaneously. Never construct a second core for the second leg, never run a second pass, and never add a switch to the shipped core. Seed with the four documented literals verbatim and zero the drift field, exactly as the spectral suite does; never invent a seed pair, because the all-zero pair is a fixed point of the generator that hangs the distribution — a hung suite here, a hang while opening a patch in Rack
  4. THE OUTPUT WRITER — a small uncompressed-audio writer. There is no such writer anywhere in this repository and no dependency is justified for one: the header is a fixed layout of a few dozen bytes. Write the header fields explicitly with a comment naming each, so a reader can check the layout without external reference

Scaling and reporting, all four required:
  - fix a STATED scale from volts to full scale and write it into the banner and into the run's own output, so nothing is silent
  - NEVER normalise per leg. Level-matching the two legs is the entire point of an A/B, and per-leg normalisation destroys it. Say so in the comment
  - count and REPORT samples that clipped, per leg, per render point, on the program's standard output, so a clipped audition is visible rather than silent
  - print a confirmation line per file naming the path and the byte count, exactly as the existing tool does

The two legs' files must be named so the operator cannot mix them up under an audio player's alphabetical sort, and the naming scheme must put the render point's label first so a pair stays adjacent.
