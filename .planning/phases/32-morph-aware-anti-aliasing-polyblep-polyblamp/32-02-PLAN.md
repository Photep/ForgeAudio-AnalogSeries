Conditioning a param into the range `forge::VcoInputs::morph` has documented since Phase 29 — post-CV, post-clamp [0,1] — is param plumbing, not DSP. FM was different: it genuinely had to enter the volt-domain summation INSIDE the core, ahead of the single exponential, which is why Phase 31's D-17 put it there and left this shell computing nothing at all.

(2) WHY NO POD FIELD IS ADDED. `forge::VcoInputs::morph` was designed post-CV/post-clamp in Phase 29 and has been stable since; Phase 31's D-05 forbids churning field semantics mid-milestone. (3) WHY THE CONDITIONING IS WRITTEN NEGATED, AND WHY THE COMPARISON-LADDER HELPER IS REJECTED HERE BY NAME. Rack does not sanitise cable voltages, and this jack is the FIRST route by which a non-finite voltage can reach `forge::Waveshape::morphedWave`. That frozen function computes `morph * 4.f` and casts the result to `int`; a float-to-int cast of a NaN is undefined behavior, and the frozen header cannot change. A ladder-shaped helper — `x < lo ? lo : (x > hi ? hi : x)` — has BOTH comparisons false for a NaN, so a NaN passes through it unchanged and the guard is inert against precisely the input class it exists to stop. The negated form puts the NaN on the fallback branch. This is the same guard SHAPE, for the same reason, as the `kVcoMaxPitchVolts` bound `forge::VcoCore` puts ahead of the frozen exponential, and it lives on this side of the frozen call for the same reason: editing the frozen header is a guardrail event, not a VCO fix.

(4) THE CORE GUARDS TOO, AND NEITHER GUARD IS REDUNDANT. Plan 32-06 hardens the same field inside `forge::VcoCore::step`, because the core must not rely on its caller — the headless harness builds `forge::VcoInputs` directly with no shell in the way. This guard exists so the POD arriving at the seam actually honours the range its own declaration promises.
